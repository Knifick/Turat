# Turat

Turat — децентрализованный (local-first) мессенджер со сквозным шифрованием (E2EE) для Windows
и Android. Identity, история сообщений, outbox и контакты принадлежат клиенту; сервер («Node») —
заменяемое, недоверенное хранилище opaque-данных: почтовых ящиков, предварительных ключей,
зашифрованных вложений и подписанных записей маршрутизации.

Вся бизнес- и криптологика реализована один раз, на общем Rust-ядре (`client/core`). Оба
нативных клиента — «тонкие» UI-оболочки: они отправляют в ядро JSON-команды через узкий ABI
(`create` / `invoke` / `destroy`) и получают в ответ неизменяемый снапшот состояния для рендеринга.
Ни Kotlin, ни C# не дублируют доменные правила.

> **Ветка `liquid-glass`** — единственная, которая развивается дальше. Здесь Windows и Android
> получили оформление в духе Liquid Glass: мягкое свечение за экранами, полупрозрачные панели,
> пузыри и кнопки, у Windows дополнительно системный acrylic-фон окна.

Независимый технический разбор кодовой базы (что реально подтверждено кодом, а что заявлено, но
не найдено) — [`TURAT_TECH_REPORT.md`](TURAT_TECH_REPORT.md). Рекомендуется прочитать перед тем,
как полагаться на Turat для чего-то серьёзного: там честно перечислены и сильные, и слабые места.

## Статус проекта коротко

- Обмен сообщениями один-на-один (E2EE, double ratchet, mailbox, вложения) — реализован и
  покрыт юнит-тестами ядра.
- Оба нативных клиента — функционально полные production-приложения, не прототипы.
- Групповые чаты (с версии 3.2.0) — реализованы в клиентском Rust-ядре поверх тех же попарных
  E2EE-каналов: роли, права, приглашения, исключение. Правила переходов состояния покрыты
  юнит-тестами, доставка — сквозным тестом на трёх клиентах через настоящий Node. Подробности —
  в разделе «Групповые чаты» ниже.
- Каналы (с версии 3.3.0) — посты для подписчиков, администраторы с правами как в Telegram,
  комментарии, реакции, просмотры, привязка группы обсуждения. Тоже в клиентском ядре поверх
  попарных E2EE-каналов, без знающего состав сервера. Правила прав покрыты юнит-тестами, полный
  цикл (подписка незнакомцев по ссылке, история, пост, комментарий через администратора,
  просмотры, удаление подписчика) — сквозным тестом на трёх клиентах через настоящий Node.
  Подробности — в разделе «Каналы» ниже.
- Серверная часть v2 реализована по большинству функций, но почти не покрыта тестами.
- Transparency-log с Merkle-checkpoint заявлен в документации, но в клиентском Rust-ядре не
  найден — судя по всему, это либо будущая работа, либо частично реализовано только на сервере
  (`RoutingV2Service`).
- **Независимый криптографический аудит не проводился.** Ratchet и hybrid-handshake (X25519 +
  ML-KEM-768) — собственная реализация поверх проверенных крейтов, а не готовая сборка Signal
  Protocol/MLS.

Подробности и методология — в [TURAT_TECH_REPORT.md](TURAT_TECH_REPORT.md).

## Что реализовано

- P-256 identity, отдельные `DeviceID`, сертификаты устройств, подписанные identity-ключом;
- link-пакеты для новых устройств без копирования master identity key, отзыв устройств и защита
  от отката `DeviceList`;
- зашифрованный (на уровне значений AES-256-GCM) SQLite event log с WAL, persistent outbox,
  at-least-once доставка и dedup;
- text/edit/delete/reaction, delivery/read receipts, pending contact requests;
- public contact inbox с отдельной capability, text-only запросами от незнакомцев и proof-of-work;
- несколько Mailbox Nodes, конверты фиксированных размерных классов (padding против анализа длины
  трафика) и раздельные capability для чтения/записи/публичного контакта;
- X25519 + ML-KEM-768 (пост-квантовый KEM) при первом согласовании, далее double ratchet с
  DH-обновлениями и кэшем пропущенных ключей;
- непересекающиеся batch предварительных ключей для разных Node;
- потоковые зашифрованные вложения (фото/видео с локальным сжатием, чанки по 512 КиБ с
  проверкой SHA-256 каждого чанка), несколько Blob Nodes;
- подписанный (Ed25519) Node descriptor с закреплением `NodeID` и HTTPS-only discovery;
- 2-of-3 Ed25519 release manifests с защитой от отката/подмены версии (детали — ниже, в разделе
  «Обновления»);
- production v2-only режим на сервере: legacy REST/WS API из первого поколения проекта
  отключается флагом и возвращает 404 (сам код первого поколения из репозитория не удалён —
  подробнее в техотчёте).

## Групповые чаты

Группа — до 100 участников. У неё нет общего ключа и нет сервера, который знал бы её состав:
каждое событие группы подписывается один раз ключом устройства автора (`conversationId` —
GroupID вида `ttg1-…`) и уходит каждому участнику по его личному double ratchet, как обычное
сообщение. Node видит только привычные конверты фиксированных размеров.

**Роли.** Владелец (ровно один), администраторы и участники.

| Действие | Кто может |
|---|---|
| Писать, отвечать, ставить реакции, выйти | любой участник, принявший приглашение |
| Приглашать | администраторы и владелец; участники — если это разрешено в правах группы |
| Менять название, описание и фото | администраторы и владелец; участники — если разрешено |
| Исключать | администратор — участников, владелец — и администраторов |
| Удалять чужие сообщения у всех | тот, кто старше автора по роли |
| Менять права участников | администраторы и владелец |
| Назначать и снимать администраторов, передавать владение | только владелец |

Владелец, выходя из группы, оставляет её старшему из оставшихся участников.

**Как проверяются изменения.** Состав, роли и права — это полное состояние группы с номером
`epoch`. Любое изменение — новое состояние с `epoch + 1`, подписанное автором. Устройство
каждого участника сравнивает его со своим и принимает только ту разницу, на которую у автора
были права **в прежнем** состоянии: участник не может в одном изменении выдать себе роль и тут
же ей воспользоваться. Подмена создателя, откат номера, изменение от бывшего участника и
изменение данных других участников отклоняются. Изменение, пришедшее раньше предыдущих,
откладывается, пока не догонят остальные (до недели). Два разных изменения с одинаковым
номером все участники разрешают одинаково — по детерминированному хешу.

**Приглашения.** В группу добавляются только принятые контакты добавляющего. Приглашённый видит
приглашение как запрос и решает сам; до принятия он не может писать, а квитанции о прочтении
не уходят. Участники группы не обязаны знать друг друга: первое событие незнакомцу уходит в его
публичный ящик (под его квотой и PoW), а вступивший рассылает всем свой личный обратный адрес.
В карточке группы участник помечен «ещё не подтвердил(а) участие», пока от него не пришло ни
одного подписанного события: состав из приглашения — лишь слова пригласившего.

**Что это даёт и чего нет.**

- Исключённый участник не получает ни одного нового сообщения: они просто больше не шифруются
  под его устройства. Отдельной ротации группового ключа не требуется — его нет.
- Прочитанное до исключения у него остаётся — как и в любом мессенджере.
- Новый участник не видит историю до своего вступления.
- Квитанции о доставке в группе не отправляются (это N² трафика); галочка значит «ушло хотя бы
  одному участнику», двойная — «прочитал хотя бы один».
- Схема не MLS и не Sender Keys: стоимость отправки растёт линейно с числом участников, отсюда
  потолок в 100 человек. Независимого аудита у групп, как и у всего проекта, нет.
- Фото группы ограничено ~24 КБ: оно едет внутри состояния и должно помещаться в публичный ящик.

## Каналы

Канал — лента постов, как в Telegram: публикуют администраторы, подписчики читают, ставят
реакции и комментируют. До 1000 подписчиков и 50 администраторов. Как и у группы, общего ключа
и сервера, который знал бы состав, нет: каждый пост подписывается один раз (`conversationId` —
ChannelID вида `ttch1-…`) и уходит каждому подписчику по его личному double ratchet.

**Подписчики друг друга не видят.** В подписанном состоянии канала перечислены только
администраторы с их правами. Список подписчиков ведут сами администраторы и сверяют его между
собой (побеждает более поздняя запись); подписчику он не приходит вовсе.

**Как подписаться.** По ссылке-приглашению `turat://channel/<ChannelID>?via=<UserID>` (её
показывает карточка канала у администратора с правом приглашать; Android открывает такие ссылки
сам) — запрос уходит администратору из ссылки через его публичный ящик, а тот присылает состояние
канала, последние 30 постов с правками и счётчики. Второй путь — приглашение из контактов: оно
приходит запросом, и подписка начинается, только когда человек его примет. Заблокированный
подписчик по ссылке не вернётся.

**Права администраторов** — те же семь, что в Telegram:

| Право | Что даёт |
|---|---|
| Публиковать посты | писать в канал |
| Редактировать чужие посты | править посты других администраторов |
| Удалять чужие посты | удалять посты и комментарии у всех |
| Приглашать подписчиков | ссылка-приглашение и приглашения контактам |
| Менять данные канала | название, описание, фото, подпись постов, комментарии, группа обсуждения |
| Удалять и блокировать подписчиков | убирать подписчиков из канала, в том числе навсегда |
| Назначать администраторов | только с правами не шире своих |

У владельца все права всегда. Администратор меняет права и разжалует только тех, кого назначил
сам (владелец — любых); свои права менять нельзя. Разжалованный остаётся подписчиком. Владелец
не может просто отписаться — только передать канал другому администратору или удалить его у всех.
Каждое изменение проверяется так же, как в группе: новое состояние с `epoch + 1` принимается,
только если у автора были права на эту разницу **в прежнем** состоянии.

**Комментарии.** Подписчики не знают адресов друг друга, поэтому комментарий уходит автору поста,
а тот пересылает его остальным вместе с исходной подписью и личностью комментатора. Подпись
проверяет каждый получатель, а UserID — это хеш ключа, так что администратор может не переслать
комментарий, но подделать или изменить — нет. Администраторы комментируют и удаляют комментарии
напрямую.

**Просмотры и реакции** уходят автору поста; он раз в две минуты (если что-то изменилось)
рассылает подписчикам итоговые счётчики вместе с числом подписчиков. Счётчики — слова автора,
проверить их подписчик не может, как и в любом мессенджере.

**Группа обсуждения.** К каналу можно привязать группу, в которой состоит администратор: новые
посты автоматически пересылаются в неё от имени канала. Комментарии под постами работают и без
неё.

**Ограничения.** Стоимость рассылки линейна по числу подписчиков: пост в канал на тысячу человек —
тысяча зашифрованных конвертов, которые фоновая синхронизация отправляет пачками. Историю старше
30 последних постов новый подписчик не получает. Подпись поста («Подписывать посты») — вопрос
отображения: автор каждого поста криптографически известен всем подписчикам всегда.

## Звонки

Аудиозвонки — только принятым контактам в личном диалоге. Приглашение, ответ и завершение
(`call.offer` / `call.ringing` / `call.answer` / `call.end`) — обычные подписанные события поверх
double ratchet, поэтому позвонить незнакомцу нельзя, а Node не знает, кто кому звонит.

**Шифрование.** Каждая сторона создаёт одноразовый ключ X25519 и передаёт его внутри
зашифрованного события. Из общего секрета HKDF-SHA256 (с солью из CallID, UserID обоих и обоих
одноразовых ключей) выводит два ключа AES-256-GCM — по одному на направление — и четыре эмодзи
для сверки. Nonce — направление и номер пакета, окно из 128 пакетов отбрасывает повторы. После
звонка ключи исчезают вместе с ним (forward secrecy).

**Голос.** Opus 48 кГц, 20 мс кадры, 32 кбит/с с встроенной коррекцией потерь (FEC):
пропавший пакет восстанавливается из следующего, а если пропало несколько подряд — маскируется.
Адаптивный джиттер-буфер (40–240 мс) подстраивается под сеть и сам сбрасывает накопленную
задержку. Android включает системное эхо- и шумоподавление.

**Связь.** Медиа идёт через ретранслятор своего Node: UDP 3479, а если UDP режут — WebSocket
поверх TLS на 443. Если канал замолкает на ≈2,5 с, клиент прямо посреди разговора переподключается другим
путём, не теряя звонок; смена сети (Wi-Fi → LTE) переживается так же.
Порвавшаяся на 25 секунд связь завершает звонок с пометкой «связь прервалась».

**Интерфейс (Android).** Кнопка трубки в шапке диалога; полноэкранный экран звонка в цветах
выбранной темы: расходящиеся волны во время вызова, кольцо и звуковая волна, которые живут от
громкости голоса, таймер с пометкой E2EE, качество связи, эмодзи для сверки ключа. Экран
сворачивается в плавающий пузырь. Входящий звонок звонит мелодией телефона и показывается поверх
экрана блокировки; идущий разговор держит сервис переднего плана с уведомлением и кнопкой
«Завершить». Каждый звонок остаётся в истории диалога: «📞 Исходящий звонок · 3:12»,
«📞 Пропущенный звонок» и т. д.

**Ограничения.** Входящий звонок приходит, пока приложение запущено (push-уведомлений у Turat нет).
Windows-клиент пока звонить не умеет: входящий звонок на нём записывается как пропущенный.
Групповых и видеозвонков нет.

## Интерфейс

UI обоих клиентов ориентируется на привычные мессенджеры: Android — на Telegram for Android
(боковое меню, пузыри с «хвостом» и временем внутри, круглая кнопка нового чата), Windows — на
Unigram (левый рельс с профилем, список чатов, контекстные меню, собственная полоса заголовка).

Доступны одиннадцать тем (Ориджин, Гранат, Обсидиан, Чёрный, Графит, Изумрудный, Океан, Янтарь,
Аметист, Облачный, Пергамент) и Liquid Glass поверх любой из них — стеклянные значения выводятся
из той же палитры, отдельного набора цветов не требуется.

- список чатов с превью, временем, галочками и счётчиком непрочитанных;
- групповые чаты: создание из контактов, приглашения, страница группы с участниками и ролями,
  служебные отметки в ленте («Алиса добавила Боба»), имя автора над сообщениями;
- каналы: создание, подписка по ссылке, посты с просмотрами, реакциями и кнопкой комментариев,
  страница канала с администраторами, их правами и подписчиками, группа обсуждения;
- закреплённые чаты, «без звука», «непрочитано», очистка истории, черновики;
- ответы с цитатой, пересылка, реакции, редактирование, удаление, мультивыбор с копированием;
- разделители дат, группировка подряд идущих сообщений одного автора;
- глобальный поиск по чатам и тексту сообщений;
- фото профиля, публикация профиля/username в directory Node;
- «последняя активность» — подписанная запись directory, по умолчанию выключена;
- Windows: Enter — отправка, Shift+Enter — перенос строки, Esc — снятие правки/ответа;
- Android: свайп вправо в диалоге — назад к списку, боковое меню — свайпом из списка.

## Структура репозитория

| Каталог | Назначение |
|---|---|
| `client/core` | Общее Rust-ядро: identity, крипто, зашифрованное SQLite-хранилище, local-first протокол, вложения |
| `client/android` | Production Android-клиент (Kotlin + Jetpack Compose, JNI) |
| `client/windows` | Production Windows-клиент (C# + WinUI 3, P/Invoke) |
| `client/TuratText.Client`, `client/TuratText.Android` | Устаревшие клиенты первого поколения — не входят в сборку, оставлены только как источник форматов для миграции локальных данных |
| `server` | Java/Spring Boot backend — содержит v1 (legacy) и v2 (local-first) API одновременно |
| `docs/` | Документация; `docs/e2ee.md`, `docs/sync.md`, `docs/database.md`, `docs/api.md` описывают только устаревшую v1-модель, `docs/local-first-v2.md` и `docs/architecture.md` — актуальную v2 |
| `tools/` | `UpdateAuthority` (подпись релизов и Android keystore), `LocalFirstSmoke` (smoke-тест протокола), генератор emoji-ассетов |
| `scripts/build-clients.ps1` | Единый pipeline полной пересборки обоих клиентов, тестов и подписи APK |

## Сборка из исходников

Полная release-сборка обеих платформ (Rust-тесты, Windows core + WinUI 3, Android core + APK с
release-подписью и проверкой):

```powershell
.\scripts\build-clients.ps1
```

Нужны: stable Rust с `cargo-ndk`, Visual Studio Build Tools с workload C++ (MSVC), .NET 8 SDK,
Android SDK 36 + NDK, JDK 17+. Gradle 9.6.1 закреплён wrapper-ом Android-проекта. Для подписи APK
нужен свой Android release-keystore в `release-secrets/android/` — сгенерировать его можно так:


## Свой Node: как захостить

Node — это единственная часть Turat, которую можно (и стоит) развернуть самостоятельно. Он не
видит открытый текст сообщений и приватные ключи — только зашифрованные конверты, зашифрованные
чанки вложений и подписанные публичные записи (маршрутизация, username, presence). Чем больше
независимых Node в сети, тем устойчивее и приватнее система в целом.

### Минимальные требования

- VPS с публичным IPv4 (IPv6 — по желанию, тогда добавьте и AAAA-запись домена).
- Домен (поддомен) с A-записью на этот IP. Без домена не получить публичный TLS-сертификат.
- Открытые порты: TCP 80/443 (HTTP-01/HTTPS), UDP 443 (HTTP/3) и UDP 3479 (голос звонков).
  Оба UDP необязательны, но желательны: без них HTTPS работает, а звонки идут через TLS на 443.
- Docker Engine + Docker Compose v2.
- Разумный минимум: 1 vCPU / 1 ГБ RAM хватает для одного Node с PostgreSQL и Caddy на небольшую
  нагрузку; для собственного продакшен-узла с запасом лучше взять 2 vCPU / 2 ГБ RAM.

### Установка

```bash
unzip TuratText-VPS-Node.zip     # из Releases этого репозитория
cd v2
chmod +x install.sh backup.sh restore.sh
./install.sh node.example.org admin@example.org "My Turat Node"
```

`install.sh` сам генерирует секреты PostgreSQL/JWT с правами `0600`, поднимает непривилегированный
контейнер Node, PostgreSQL 17 и Caddy, получает TLS-сертификат и ждёт успешного `/v2/health`.
Полная пошаговая инструкция, проверки после установки, backup/restore и порядок обновлений — в
[`docs/vps-bootstrap.md`](docs/vps-bootstrap.md).

### Практические советы по хостингу собственного Node

- **Провайдер.** Подойдёт любой VPS с честным исходящим трафиком без DPI-фильтрации мессенджеров;
  для устойчивости к блокировкам лучше выбирать провайдера/юрисдикцию, никак не связанную с той,
  где уже размещён официальный Node (`turattext.rplacefree.store`) — так вы добавляете сети
  реальную независимость, а не второй узел за тем же провайдером.
- **Домен отдельно от VPS.** Держите домен у отдельного регистратора/DNS-провайдера — если сам VPS
  заблокируют по IP, вы быстро переставите A-запись на новый сервер, не теряя `NodeID` (он привязан
  к identity-ключу Node, а не к IP или домену).
- **`.env` и `node-data` — самое ценное на сервере.** `.env` содержит пароль PostgreSQL и JWT-секрет,
  `node-data` — приватный Ed25519-ключ identity Node. Их компрометация не раскрывает переписку
  пользователей (она E2EE), но позволяет выдать себя за ваш Node или уронить его. Регулярно делайте
  `./backup.sh` и уносите зашифрованную копию за пределы VPS (другой провайдер/облако/локально) —
  без бэкапа `node-identity` после аварии Node придётся поднимать с новым `NodeID`, и все клиенты,
  закрепившие старый, потеряют к нему доверие.
- **Не открывайте лишние порты.** `docker-compose.yml` уже собирает Postgres и Node во внутреннюю
  сеть `backend` без публикации портов наружу — наружу торчит только Caddy на 80/443. Не меняйте
  это без необходимости и не выставляйте PostgreSQL в интернет.
- **Rate limiting и proof-of-work уже включены по умолчанию** (`TURATTEXT_V2_REGISTRATION_POW_BITS`,
  `TURATTEXT_V2_ENVELOPE_POW_BITS`, `TURATTEXT_V2_CONTACT_POW_BITS`, `TURATTEXT_V2_REQUESTS_PER_MINUTE`
  в `docker-compose.yml`) — это защита от спама и флуда на уровне протокола, а не UDP/SYN-флудов;
  от объёмных DDoS-атак на сетевом уровне спасает только защита провайдера/CDN перед Caddy.
  Понижать PoW-биты стоит только для собственных тестов, не для публичного Node.
  `TURATTEXT_V2_TRUST_FORWARDED_FOR=true` рассчитан именно на схему «Caddy перед Node» — если
  добавите ещё один reverse proxy или CDN перед Caddy, либо уберите его вовсе, либо явно проверьте,
  что `X-Forwarded-For` не подделывается снаружи.
- **Мониторинг вместо угадывания.** `/v2/health` и `/v2/node-descriptor` — открытые эндпоинты,
  их удобно опрашивать внешним uptime-мониторингом (например, раз в 1–5 минут) и получать алерт при
  падении. `docker compose logs -f --tail=100 node caddy` — первое, куда смотреть при инциденте.
- **Второй независимый Node — не копия первого.** Для второго узла берите отдельный VPS/домен и
  запускайте `install.sh` заново: он обязан сгенерировать собственный `NodeID`. Копирование
  `node-data` первого Node на второй сервер создаст двух Node с одинаковой identity — это ломает
  модель доверия, а не резервирует её.
- **Обновления Node не требуют пересборки клиентов.** `docker compose pull && docker compose up -d
  --build` — Docker-образ Node обновляется независимо от подписанных релизов Windows/Android
  (`updates/stable/manifest.json`), которые раздаются той же Caddy, но управляются отдельно через
  `UpdateAuthority` офлайн-ключами (см. [`docs/vps-bootstrap.md`](docs/vps-bootstrap.md), раздел
  «Обновления»). Volumes `postgres-data`, `node-data`, `caddy-data` и файл `.env` нельзя удалять
  при обычном обновлении.
- **Официальный клиент подключается к вашему Node не автоматически.** По умолчанию оба клиента
  используют `https://turattext.rplacefree.store` как bootstrap. Добавить свой Node пользователи
  могут вручную в разделе «Сеть и приватность» — сообщите им домен вашего узла напрямую, публичного
  автообнаружения независимых Node в клиенте нет.

## Обновления из приложения

Оба клиента сами проверяют [Releases](https://github.com/Knifick/Turat/releases) официального
репозитория: через несколько секунд после запуска и дальше раз в 6 часов. Черновики и
pre-release пропускаются, номер версии берётся из тега (`v3.1.0-liquid-glass` → `3.1.0`) и
сравнивается с версией установленного клиента.

- Над списком чатов появляется одна строка «Доступна версия X». Её можно скрыть крестиком до
  следующего запуска.
- По нажатию открывается ченджлог (описание релиза на GitHub) и три кнопки: «Обновить», «Позже»
  и «Пропустить эту версию». О пропущенной версии клиент больше не напоминает, о следующей —
  напомнит.
- В настройках, в разделе «Данные», есть ручная проверка. Она снова предлагает даже пропущенную
  версию.

Перед установкой клиент сверяет SHA-256 загруженного файла с хешем, который GitHub публикует для
каждого файла релиза, или со строкой из `SHA256SUMS.txt`. Файл без известного хеша не
устанавливается.

- **Android** скачивает `Turat.apk` и передаёт его системному установщику (`PackageInstaller`).
  Android дополнительно проверяет, что APK подписан тем же release-ключом, что и установленное
  приложение. При первом обновлении система попросит разрешить Turat устанавливать приложения.
- **Windows** скачивает `Turat-win-x64.zip`, распаковывает `Turat.exe`, переименовывает запущенный
  exe в `Turat.exe.old`, ставит новый на его место и перезапускается. Новая версия ждёт выхода
  старой и удаляет `.old`. Если в папку приложения нельзя писать или сборка многофайловая,
  проверенный `Turat.exe` открывается в проводнике для ручной замены. Authenticode-подписи у
  Windows-сборки нет, поэтому её подлинность держится только на HTTPS и хеше GitHub.

Чтобы клиенты увидели новый релиз:

1. поднимите версию: `versionCode`/`versionName` в `client/android/app/build.gradle.kts` и
   `Version`/`AssemblyVersion`/`FileVersion` в `client/windows/TuratText.Windows.csproj`;
2. соберите `scripts/build-clients.ps1`;
3. опубликуйте обычный (не draft и не pre-release) релиз с тегом вида `vX.Y.Z…` и файлами
   `Turat.apk`, `Turat-win-x64.zip` и `SHA256SUMS.txt`. Описание релиза и есть ченджлог.

Этот механизм не заменяет подписанные 2-of-3 release manifests на Node, а работает рядом с ними.

## Нативные клиенты

- `client/core` — единое Rust-ядро: identity, зашифрованное SQLite/WAL-хранилище, local-first
  состояние, контакты, сообщения, вложения, backup/device-link, проверка Node descriptor и
  directory-записей. Публичная граница — JSON-команды поверх C ABI; Android использует JNI,
  Windows — P/Invoke.
- `client/android` — Kotlin + Jetpack Compose + Material 3. Ключ локального vault оборачивается
  Android Keystore; Rust `.so` собирается для `arm64-v8a` и `armeabi-v7a`.
- `client/windows` — C# + XAML + WinUI 3 на стабильном (не experimental) Windows App SDK 2.4.0.
  Ключ vault защищён DPAPI текущего пользователя. На момент этого README `PublishSingleFile` в
  `.csproj` выключен (`false`), поэтому публикуемый пакет — не единый EXE-файл, а каталог с
  зависимостями рядом (см. `TURAT_TECH_REPORT.md`, раздел 5.4).

Старые `client/TuratText.Client` и `client/TuratText.Android` не входят в production-сборку и
оставлены только как источник форматов v2 для миграции существующих локальных данных.

## Граница безопасности

Реализация функционально завершает v2 vertical slice для обмена один-на-один, групп и каналов,
но **не проходила независимый криптографический аудит**. Ratchet, групповой и канальный control
plane (подписанные состояния с проверкой прав, `client/core/src/core/groups.rs` и
`client/core/src/core/channels.rs`) — собственная реализация, а не сертифицированная сборка
Signal Protocol/MLS. `TURAT_TECH_REPORT.md` написан до появления групп и каналов и описывает
состояние на версию 3.1. До любого публичного high-risk запуска нужны внешний аудит, fuzzing
подписываемых форматов и нагрузочные испытания нескольких независимых Node.
