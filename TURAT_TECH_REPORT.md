# Технический отчёт о проекте Turat (TuratText)

*Дата анализа: 13 сентября 2026 г. Анализ выполнен по исходному коду репозитория (ветка `liquid-glass`), без внесения изменений в код. Заявления документации (README, docs/) сверялись с фактическим кодом.*

---

## 1. Назначение проекта

**Turat (TuratText)** — мессенджер с сквозным шифрованием (end-to-end encryption, E2EE), состоящий из:

- нативного клиента для **Windows** (C# / WinUI 3);
- нативного клиента для **Android** (Kotlin / Jetpack Compose);
- сервера **v2 Node** (Java / Spring Boot) — вспомогательного, не доверенного узла хранения зашифрованных данных;
- общего кроссплатформенного **Rust-ядра**, реализующего всю криптографию, локальное хранилище и сетевой протокол для обоих клиентов.

Проект существует в двух архитектурных поколениях:

1. **v1 (legacy MVP)** — классическая клиент-серверная схема: PostgreSQL, JWT-аутентификация, REST + WebSocket, ECDH-шифрование сообщений «на лету» без функций полноценного мессенджера уровня Signal.
2. **v2 (текущая, "local-first")** — децентрализованная модель, в которой идентичность, история сообщений и очередь отправки принадлежат клиенту, а сервер — заменяемый «Node», хранящий только непрозрачные (opaque) зашифрованные данные: почтовые ящики (mailbox), предварительные ключи (prekeys), blob-вложения и подписанные записи маршрутизации.

Judging by README и `docs/local-first-v2.md`, проект целенаправленно движется от v1 к v2, при этом **код v1 не удалён**, а сосуществует в той же серверной кодовой базе и отключается только конфигурационным флагом (см. раздел 5).

## 2. Структура репозитория

| Каталог | Назначение |
|---|---|
| `client/core` | Общее Rust-ядро (крипто, хранилище, сеть, протокол v2) |
| `client/android` | Production Android-клиент (Kotlin + Jetpack Compose) |
| `client/windows` | Production Windows-клиент (C# + WinUI 3) |
| `client/TuratText.Client`, `client/TuratText.Android` | Устаревшие клиенты (Avalonia/.NET MAUI-подобные), оставлены только для миграции локальных данных старого формата, в сборку не входят |
| `server` | Java/Spring Boot backend — содержит одновременно v1 и v2 API |
| `docs/` | Документация (частично устарела — см. раздел 7) |
| `tools/` | Вспомогательные утилиты: генератор emoji-ассетов, подписант обновлений (`UpdateAuthority`), smoke-тест local-first протокола |
| `scripts/build-clients.ps1` | Единый пайплайн полной пересборки обоих клиентов и проверки подписи APK |
| `release-secrets/` | Офлайн-ключи подписи Android/обновлений (намеренно исключены из репозитория в реальном использовании) |

Грубая оценка объёма кода (без каталогов сборки `bin/obj/build/target`):

| Подсистема | Строк кода (~) |
|---|---|
| Rust-ядро (`client/core/src`) | 7 900 |
| Java-сервер (`server/src`) | 7 800 |
| Android (Kotlin) | 5 800 |
| Windows (C#/XAML) | 4 700 |

История Git состоит всего из **двух коммитов** (оба соавторства с «Claude Opus 5»), то есть в репозитории нет пошаговой истории разработки — либо история была сброшена/сквошена, либо основной объём кода был перенесён из другого источника единовременно. Для отчёта о текущем состоянии кода это не критично, но стоит иметь в виду, что судить о процессе разработки по `git log` здесь нельзя.

## 4. Архитектура и принцип взаимодействия компонентов

### 4.1 Общая схема (v2)

```
┌─────────────────┐        JSON-команды        ┌──────────────────────┐
│  Android UI      │ ───── JNI (create/invoke/  │                      │
│  (Compose)       │        destroy) ──────────▶│                      │
└─────────────────┘                              │   Rust-ядро (core)   │
                                                  │  identity, crypto,   │
┌─────────────────┐        P/Invoke              │  SQLite-хранилище,   │
│  Windows UI      │ ───── (source-generated,    │  outbox, ratchet,    │
│  (WinUI 3)       │        create/invoke/       │  сетевой клиент      │
└─────────────────┘        destroy) ────────────▶│                      │
                                                  └──────────┬───────────┘
                                                             │ HTTPS (HTTP/2→HTTP/3)
                                                             ▼
                                      ┌──────────────────────────────────────┐
                                      │        v2 Node (Java/Spring)         │
                                      │  mailbox · prekeys · blobs · routing │
                                      │  · usernames · presence · transpar-  │
                                      │  ency-log (Merkle) · node-descriptor │
                                      └──────────────────┬────────────────────┘
                                                          │ JDBC
                                                          ▼
                                                    PostgreSQL 17
```

Ключевая идея: **бизнес-логика реализована один раз**, на Rust. И Android, и Windows — это «тонкие» UI-оболочки: они отправляют в ядро JSON-команды вида `{"command":"send_text", ...}` и получают в ответ полный неизменяемый снапшот состояния (`snapshot`) для немедленного рендеринга. Ни Kotlin, ни C# не дублируют доменные правила — это подтверждено кодом (`NativeCore.kt`, `Interop/RustCore.cs`): оба используют один и тот же протокол `create/invoke/destroy` с JSON-полезной нагрузкой.

Сервер («Node») в модели v2 **не хранит и не видит открытый текст сообщений и приватные ключи** — только зашифрованные конверты (mailbox), зашифрованные чанки вложений (blob) и подписанные публичные записи (маршрутизация, username, presence). Он заменяем: клиент проверяет подпись Node-дескриптора (Ed25519) и его `NodeID`, а не доверяет серверу как таковому.

### 4.2 Клиент-серверный протокол v2 (по коду сервера)

Реальные HTTP-эндпоинты, зарегистрированные в Java-коде под префиксом `/v2/`:

- `POST /v2/mailboxes`, `PUT/GET /v2/mailboxes/{id}/envelopes`, `POST /v2/mailboxes/{id}/ack` — почтовые ящики с конвертами;
- `PUT/GET /v2/prekeys/...` — предварительные ключи для асинхронного согласования сессий;
- `PUT/GET /v2/presence/{userId}` — статус «последняя активность»;
- `PUT/GET /v2/profiles/{userId}` — публичный профиль;
- `PUT/GET /v2/usernames/{username}`, `GET /v2/usernames/by-user/{userId}` — привязка username к идентичности;
- `PUT/GET /v2/routing/{userId}`, `GET /v2/transparency/operations`, `GET /v2/transparency/checkpoint` — маршрутизация устройств и transparency-лог;
- `POST /v2/blobs`, `PUT/GET /v2/blobs/{objectId}/chunks/{n}`, `GET /v2/blobs/{objectId}/manifest` — зашифрованные вложения по чанкам;
- `GET /v2/node-descriptor`, `GET /v2/health`.

### 4.3 Формат сообщений между UI и ядром

Пример команды (из `client/README.md`, подтверждён в обоих клиентах):

```json
{"command":"send_text","user_id":"tt1-…","text":"Привет"}
{"command":"react","event_ids":["evt1-…"],"reaction":"👍"}
{"command":"sync"}
```

Ответ всегда содержит `ok`, опциональный `error`, `value` и полный `snapshot`.

## 5. Разбор по компонентам

### 5.1 Rust-ядро (`client/core`)

Ядро — самая зрелая часть проекта: **TODO/FIXME/`unimplemented!()` в коде не встречаются ни разу**, повсюду системная обработка ошибок через единый тип `CoreError` (`thiserror`), присутствуют юнит-тесты на криптографические сценарии.

Подтверждено кодом (реализовано):

- **Идентичность**: P-256 ключи, `UserID = tt1-SHA256(SPKI)`, `DeviceID = ttd1-SHA256(SPKI)`, сертификаты устройств, подписанные identity-ключом (`identity.rs`, `protocol.rs`).
- **Гибридное согласование ключей и двойной храповик**: X25519 + ML-KEM-768 (пост-квантовый KEM) в начальном рукопожатии (`prekeys.rs`, `ratchet.rs`), далее классический double ratchet с DH-обновлениями, кэшем «пропущенных» ключей (до 2000) и AEAD; есть тесты на полный диалог, доставку не по порядку и отклонение подделанного сообщения.
- **Локальное хранилище**: SQLite (bundled `rusqlite`) в режиме WAL; append-only outbox с экспоненциальными ретраями; при этом шифруется AES-256-GCM **не сам файл БД**, а содержимое (JSON-полезная нагрузка) каждого события/контакта/профиля перед вставкой — то есть это не полноценный аналог SQLCipher (файл БД на диске не зашифрован целиком), а шифрование на уровне значений.
- **Проекции сообщений**: text/edit/delete/reaction/attachment, delivery/read receipts.
- **Вложения**: потоковый AES-GCM-контейнер (`media.rs`), чанковая загрузка на несколько Blob Nodes по 512 КиБ с проверкой SHA-256 каждого чанка (`blobs.rs`).
- **Бэкапы и связывание устройств**: пароль → Argon2 → AES-256-GCM для `CreateBackup`/`RestoreBackup` (магический заголовок `TTBACKUP3`) и `CreateDeviceLink`/`ImportDeviceLink` (`TTLINKV3`), без передачи мастер-ключа устройства.
- **Node discovery и проверка подписей**: обязательный HTTPS (кроме localhost), кэширование и Ed25519-проверка дескриптора Node, проверка P-256-подписей username/профиля/presence/маршрутизации.
- **Mailbox-протокол**: конверты с паддингом до фиксированных размерных классов (защита от анализа длины трафика), раздельные capability для чтения/записи/публичного контакта.

Не подтверждено кодом (заявлено в README/docs, но не найдено в `client/core`):

- **`.ttenv` / `.ttbridge` форматы** — команды экспорта/импорта существуют, но пишут обычный JSON без специфичных расширений или магических констант; возможно, реализовано только на уровне UI/имени файла, а не в ядре.
- **Группы (epoch control plane) и transparency-log с Merkle-checkpoint** — по всему `client/core/src` поиск по `merkle|transparency|checkpoint|epoch|group` не дал совпадений. Групповые чаты и transparency-логика в ядре **отсутствуют** — судя по всему, transparency-log реализован только на сервере (см. 5.2), а групповые чаты в клиентском коде не найдены вовсе, несмотря на заявление README о «group epoch control plane».

Тестовое покрытие: юнит-тесты есть в большинстве модулей (ратчет, маршрутизация, mailbox, медиа, ядро), но интеграционный e2e-тест (`tests/delivery.rs`, два клиента через реальный Node) помечен `#[ignore]` и не запускается по умолчанию — то есть межмодульная работоспособность подтверждена только юнит-тестами по отдельности.

### 5.2 Сервер (`server`, Java/Spring Boot)

Кодовая база одновременно содержит:

- **Legacy v1**: `AuthController` (`/api/auth/*` — регистрация/логин/refresh на JWT), `ChatController`, `MessageController`, `UserController`, `KeyController`, `ServerController` (репликация PRIMARY/MIRROR), `ReplicationController`, `AdminController`, WebSocket-обработчик (`/ws`) — полностью рабочий REST+WS слой поверх PostgreSQL/JPA/Hibernate с Flyway-миграциями (схема из `docs/database.md` подтверждается: `users`, `chats`, `messages`, `servers` и т.д.).
- **v2**: 9 контроллеров в пакете `com.turattext.v2` (Mailbox, Prekey, Presence, Profile, Username, Routing, Blob, Node, Health) поверх отдельных таблиц `v2_*` (добавлены миграциями V5–V11 **поверх** старой схемы, а не взамен неё).

Механизм отключения legacy API — не удаление кода, а **рантайм-фильтр** `V2OnlyAndRateLimitFilter` (`@Order(HIGHEST_PRECEDENCE)`): если свойство `turattext.v2.only=true`, любой путь, не начинающийся с `/v2/`, возвращает `404`. По умолчанию в `application.yml` это `false` (legacy API открыт), а в `server/deploy/v2/docker-compose.yml`, то есть в реальном production-развёртывании, явно выставлено `TURATTEXT_V2_ONLY=true`. Иными словами, заявление README «production v2-only режим: legacy API возвращает 404» подтверждается конфигурацией деплоя, но не архитектурой кода — v1 полностью присутствует и лишь выключается флагом.

Реально реализованные (не заглушки) v2-сервисы, подтверждённые прочтением кода:

- `MailboxV2Service` — конверты фиксированных размерных классов, раздельные capability-хэши (read/write/contact), long-poll выдача через `DeferredResult`, TTL/квоты, опциональный proof-of-work.
- `BlobV2Service` — чанковая загрузка с проверкой SHA-256 каждого чанка, лимиты размера.
- `NodeIdentityService` — генерация/персистентность Ed25519-ключа ноды, подписанный канонический `NodeDescriptor`.
- `RoutingV2Service` — append-only `v2_transparency_operations` с автоинкрементным sequence, вычисление Merkle-корня по хэшам payload, проверка anti-rollback по DeviceList-сиквенсам.

Не найдено в Java-коде: отдельных типов дескрипторов Relay/Discovery (заявлены в README как отдельные сущности) — судя по всему, их функцию выполняет тот же Node-дескриптор, либо это нереализованная часть плана. HTTP/2/HTTP/3 полностью реализованы средствами Caddy (обратный прокси), в самом Java-коде специфичной конфигурации протокола не обнаружено.

Тестовое покрытие сервера — минимальное: всего 2 тестовых класса (`AdminAuthServiceTest`, `ReplicationCryptoTest`), оба про v1/инфраструктуру; v2-функциональность (mailbox/blob/routing) тестами не покрыта вовсе.

### 5.3 Android-клиент (`client/android`)

Полностью на Kotlin + Jetpack Compose, без единого XML-layout (только векторные иконки и файлы шрифтов в ресурсах) — заявление об отказе от legacy Android Views подтверждено. TODO/заглушек в коде не найдено.

Реализовано (подтверждено кодом):

- JNI-граница `NativeCore` (`nativeCreate/nativeInvoke/nativeDestroy`) плюс расширения для потокового чтения медиа (`nativeMediaOpen/Length/Read/Close`) и long-poll ожидания конвертов (`nativeWaitForEnvelopes`).
- Ключ хранилища оборачивается AES/GCM-ключом из `AndroidKeyStore`, сырой ключ обнуляется после передачи в ядро.
- MVVM: единый `StateFlow<AppSnapshot>`, все действия идут через мьютекс-защищённый вызов ядра.
- Онбординг, поиск/добавление контактов, лента сообщений, мультивыбор, реакции, редактирование/удаление, профиль, настройки Node/приватности — всё подтверждено конкретными компонентами и обработчиками.
- Вложения: выбор файла, сжатие фото (EXIF-поворот) и видео (Media3 Transformer) перед отправкой, индикатор прогресса, просмотр (zoomable-изображение, видео/аудио через ExoPlayer с собственным `DataSource`, читающим прямо из зашифрованного файла без расшифровки на диск), сохранение через Storage Access Framework.
- Адаптивный layout: порог `720.dp` переключает интерфейс между «список и чат раздельно» (телефон) и «оба видны одновременно» (широкий экран).
- Тема Liquid Glass (`Glass.kt`: анимированный фон-«аврора», стеклянные поверхности) и ровно 11 тем (`enum class AppTheme`), плюс 6 вариантов шрифта — всё подтверждено.

Частично подтверждено / не проверено детально: backup и device-link — инфраструктура экспорта/импорта файлов с паролем через SAF присутствует, но конкретные экраны вызова не разбирались построчно агентом-анализатором (файл настроек велик, 926 строк).

Не найдено: **запись голосовых сообщений** — `MediaRecorder`/`AudioRecord` в коде отсутствуют. Аудио поддерживается только как принимаемый/воспроизводимый тип вложения через тот же видеоплеер, не как отдельная функция записи голоса.

### 5.4 Windows-клиент (`client/windows`)

C# + WinUI 3 на стабильном (не experimental) Windows App SDK 2.4.0. Код выглядит завершённым и плотным (`MainWindow.xaml.cs` — 1370 строк реальной логики, не шаблонный код).

Реализовано (подтверждено кодом):

- P/Invoke через source-generated `[LibraryImport]` на `turattext_core_create/invoke/destroy/string_free/wait_for_envelopes/media_*`, с UTF-8 маршалингом строк и кастомным `DllImportResolver`, ищущим DLL в `native/` рядом с исполняемым файлом.
- Ключ хранилища защищён Windows DPAPI (`ProtectedData.Protect/Unprotect`, `CurrentUser`), обнуляется после использования.
- Флаг `--core-smoke` реально существует в `Program.cs` и проверяет ABI без открытия окна.
- Полный набор функций мессенджера: закреплённые чаты, отключение звука, черновики, ответы с цитатой, пересылка, реакции, редактирование/удаление, мультивыбор с копированием, разделители дат и группировка сообщений, глобальный поиск (debounce 280 мс), фото профиля, публикация username, тумблер presence, автосинхронизация с адаптивным интервалом (20с онлайн / 6с при активности).
- Клавиатурные сокращения: Enter — отправка, Shift+Enter — перенос строки, Esc — снятие правки/ответа — всё подтверждено в обработчике `ComposerInput_KeyDown`.
- **Liquid Glass — не косметика, а системный API**: `SystemBackdrop = new DesktopAcrylicBackdrop()` (реальный WinUI 3 acrylic) в сочетании с полупрозрачными кистями, производными от палитры темы. Ровно 11 тем в `ThemeCatalog`, как и на Android.

Расхождения с документацией:

- **README заявляет «self-contained single-file EXE», но в `.csproj` явно указано `<PublishSingleFile>false</PublishSingleFile>` и `<PublishTrimmed>false</PublishTrimmed>`.** То есть на момент анализа публикация технически не собирается как единый файл (вероятно, временно отключено из-за известных ограничений совместимости WinUI 3 с single-file publish). Это единственное найденное существенное расхождение между заявлением README и содержимым Windows-проекта.
- Визуальная цитата при ответе на сообщение (`ReplyAuthor`/`ReplyText` в XAML) отображается, но обработчик клика для перехода к оригинальному сообщению («jump-to-original», заявлен в README) в коде не найден — вероятно, не реализован, только показ текста цитаты.

## 6. Модель безопасности и её заявленная зрелость

Собственные слова проекта (`README.md`, раздел «Граница безопасности») **честно указывают на ограничения**:

- Реализация «функционально завершает v2 vertical slice», но **не проходила независимый криптографический аудит**.
- Ratchet- и group-epoch-слой — собственная реализация, а не сертифицированная сборка Signal Protocol / MLS.
- До публичного high-risk запуска заявлена необходимость внешнего аудита, fuzzing подписываемых форматов и нагрузочных испытаний нескольких независимых Nodes.

Это подтверждается и находками анализа:

- Криптографические примитивы (P-256, X25519, ML-KEM-768, AES-256-GCM, Ed25519, Argon2) — реальные, из проверенных крейтов (`ed25519-dalek`, `x25519-dalek`, `ml-kem`, `p256`, `aes-gcm`, `argon2`), не самописные.
- Но композиция протокола (double ratchet + гибридный PQ-handshake, group epoch control plane) — собственная разработка, не готовая библиотека уровня `libsignal`.
- Групповой E2EE control plane и transparency-log **заявлены в README/docs, но не найдены в клиентском Rust-коде** — либо это будущая работа, либо частично реализовано только на сервере (transparency-лог с Merkle-корнем реально есть в `RoutingV2Service`, но без клиентского клиентского counterpart в `client/core` для группового epoch-слоя).
- Тестовое покрытие критичной криптографии (ратчет, прекеи, mailbox) — юнит-тестами хорошее; интеграционное — фактически отсутствует (e2e-тест помечен `#[ignore]`), а серверная v2-логика вообще не покрыта тестами.

## 7. Соответствие документации фактическому коду

Один из значимых выводов анализа: **документация в `docs/` неоднородна по актуальности**.

- `docs/e2ee.md`, `docs/sync.md`, `docs/database.md`, `docs/api.md` описывают **только старую v1-модель** (ECDH без ratchet, PostgreSQL со видимыми метаданными, JWT, WebSocket, репликация PRIMARY/MIRROR с промоушеном мирроров). Эти документы прямо констатируют собственную незавершённость («This MVP is not a full Signal implementation», «Production upgrades: Signal Protocol / Double Ratchet» и т.д.) — то есть описывают именно то, что позже было заменено v2-архитектурой, но сами документы не были обновлены и без контекста могут ввести в заблуждение читателя, решившего, что это текущее состояние всего проекта.
- `docs/local-first-v2.md` и `docs/architecture.md`, напротив, точно описывают v2 и хорошо соответствуют найденному коду.
- README.md (актуальный, отражает состояние на ветке `liquid-glass`) в целом подтверждается кодом, за следующими исключениями:
  1. Групповые чаты / group epoch control plane / transparency-log — не найдены в клиентском Rust-ядре (сервер частично их поддерживает).
  2. `.ttenv`/`.ttbridge` как специфичные форматы файлов — не подтверждены в ядре (есть только общий JSON-экспорт/импорт).
  3. Windows self-contained single-file EXE — на уровне `.csproj` отключено (`PublishSingleFile=false`).
  4. «Encrypted SQLite» на практике — это шифрование значений в обычной (незашифрованной как файл) базе SQLite, а не файловое шифрование в духе SQLCipher.

Таким образом, README **не является фикцией и не завышает возможности радикально** — подавляющее большинство перечисленных функций подтверждено реальным, зрелым, протестированным (на уровне юнит-тестов) кодом, но несколько пунктов (групповые чаты/transparency в ядре, специфичные форматы бандлов, single-file публикация Windows) на момент анализа не подтверждаются кодом либо отключены конфигурацией.

## 8. Степень готовности проекта

| Аспект | Оценка |
|---|---|
| Направление сообщений один-на-один (E2EE, ratchet, mailbox, blob-вложения) | Реализовано и работоспособно на уровне кода, покрыто юнит-тестами |
| Оба нативных клиента (Windows, Android) | Функционально полные production-приложения с общим UX (пункты меню, темы, жесты), не прототипы |
| Серверная часть v2 | Реализована по большинству заявленных функций, но почти не покрыта тестами |
| Легаси v1 | Полностью присутствует и включаем/выключаем одним флагом — не удалено, что увеличивает поверхность атаки/поддержки, если флаг когда-нибудь будет забыт |
| Групповые чаты и transparency-log на клиенте | Не найдены в текущем клиентском коде, несмотря на заявления в README |
| Независимый аудит безопасности | Не проводился (прямо признано в самом README) |
| Интеграционное/нагрузочное тестирование | Практически отсутствует (e2e-тест отключён, v2-сервер не тестируется) |
| Готовность к публичному запуску с высоким риском | Сам проект оценивает себя как не готовый («До публичного high-risk запуска необходимы внешний аудит, fuzzing… нагрузочные испытания») |

**Общий вывод**: Turat — это не учебный черновик, а достаточно зрелая, самостоятельно спроектированная реализация мессенджера с современной криптографией (включая пост-квантовый компонент ML-KEM-768) и децентрализованной серверной моделью. Основная бизнес- и криптологика вынесена в единое, хорошо протестированное на уровне модулей Rust-ядро, вызываемое из двух полноценных нативных UI-клиентов через узкий ABI. Слабые места на момент анализа — это тестовое покрытие интеграционного уровня, несколько заявленных, но не подтверждённых в клиентском коде функций (группы, transparency на клиенте, специфичные форматы бандлов), устаревшая часть документации (v1-доки) и признанное самим проектом отсутствие независимого аудита безопасности.

## 9. Методология анализа

Отчёт подготовлен путём:

1. Изучения README.md и всех файлов в `docs/` с последующей сверкой заявлений с кодом (а не приёма их на веру).
2. Построчного и структурного анализа исходного кода Rust-ядра (`client/core/src`), Java-сервера (`server/src/main/java`), Android-приложения (`client/android/app/src/main/java`) и Windows-приложения (`client/windows`), включая файлы зависимостей (`Cargo.toml`, `build.gradle.kts`, `.csproj`) и конфигурации (`application.yml`, `docker-compose.yml`).
3. Поиска маркеров незавершённости (TODO, FIXME, `unimplemented!()`, заглушки) по всем модулям.
4. Изучения тестовых наборов (`client/core/tests`, `server/src/test`) для оценки реального, а не декларируемого качества.
5. Анализа истории Git (количество коммитов, авторство) для понимания происхождения кодовой базы.

Код репозитория не изменялся; все выводы основаны на его текущем состоянии на момент анализа.
